# BUG-008 · P1 · 旧 socket 的 `disconnect` 会把「已由新连接接管」的玩家标记为掉线

> 发现：2026-10-26 · 报告人：quality-lead（严守真）· 阶段：Wave 0 / GATE-0 独立门控
> 状态：**FIXED（主症状，v2 复议已独立验证）／覆盖面缺口转 P2-11** · 归属：`engineering-lead` · 与 BUG-004（rejoin 令牌校验）同一条链路
> v2 更新（2026-10-26）：`handleDisconnect()` 增加 `socket.stale || player.socketId !== socket.id` 归属校验，
> `disconnect` 改为「先校验归属 → 再 `clearPlayerTimers` → 再 `handleDisconnect`」，`rejoin` 给旧 socket 打 `stale`。
> QA 独立复核：① 把两道守卫同时改成 `if (false)` → 我的 `回归 BUG-008` 用例变红（1 红）；
> ② 分别只关一道守卫 → **都不变红**，说明 `stale` 与 `socketId` 归属校验互为冗余，
> 真正拦住本缺陷的是 `player.socketId !== socket.id`；`stale` 在 disconnect 路径上没有增加防护。
> ③ 该修法**没有吊销旧连接的写权限** → 旧 socket 仍可出牌、可把玩家踢出 waiting 房，已单列 **P2-11 / P2-11b**。

## 1. 一句话
`rejoin` 只更新 `player.socketId`，没有让旧连接失效；旧 socket 的 `disconnect` 事件稍后到达时，`handleDisconnect()` 仍按 `socket.playerId` 找到同一玩家并置 `player.connected = false`，于是**玩家实际在线，却被当成掉线**。

## 2. 用户可见后果
1. 该玩家的后续 `state` 广播被 `broadcastState()` 的 `if (socket && p.connected)` 跳过 → **界面冻结不再刷新**（人还在房间里），玩家会以为游戏卡死。
2. 若此刻正好轮到他：`handleDisconnect()` 会按 `disconnectedTurnMs = 8s` 调度快速托管 → **本人明明在线，却被 8 秒托管出牌**。
3. 他人视角看到该玩家「掉线」徽标（`renderRoom` / 座位信息），误导房主。
4. 宽限期 60s 后：`waiting` 阶段会被 `engine.removePlayer` 移出房间（用户莫名其妙被踢）；`playing` 阶段若全员被判离线，房间会被整房回收。

## 3. 触发条件与真实概率
移动端最常见的乱序：手机切换 App / 锁屏 → 旧连接掉线 → 前端 `reconnect` 立即 `rejoin`（新 socket id）→ **旧 socket 的 `disconnect` 事件晚于 `rejoin` 到达服务端**。Socket.IO 的重连是「新会话 + 新 id」，服务端两条事件的处理顺序并不保证与客户端发生顺序一致，因此这是可稳定复现的乱序窗口，不是理论问题。

## 4. 位置
| 文件 | 行 | 说明 |
|---|---|---|
| `net/net.js` | 310-331 | `rejoin` 更新 `player.socketId` / `socket.playerId`，但未标记旧连接作废 |
| `net/net.js` | 441-473 | `handleDisconnect()` 仅按 `socket.playerId` 定位玩家，不校验 `player.socketId === socket.id` |
| `net/net.js` | 475-478 | `disconnect` 事件无条件调用 `clearPlayerTimers(socket.playerId)` + `handleDisconnect(socket)`；`clearPlayerTimers` 同样不校验归属，**会清掉新连接刚排好的托管定时器** |

## 5. 复现步骤（协议层）
1. 3 人房开局，房主 `p0` 的 socket 记为 `A`。
2. `A` 发 `disconnect`（服务端 `connected=false`）。
3. 新 socket `B` 用正确 `rejoinToken` 发 `rejoin` → `connected=true`、`player.socketId='B'`。
4. 新 socket `C` 再用同一 token 发 `rejoin` → `player.socketId='C'`（幂等，符合预期）。
5. **`B` 发 `disconnect`**（模拟幽灵连接的迟到事件）。
6. 实际：`player.connected === false`，而 `C` 仍在线且 `player.socketId === 'C'`。
   预期：`connected` 应保持 `true`。

## 6. 已固化为回归用例
`test/net.adversarial.test.js` → `缺陷 P1-02：旧 socket 的 disconnect 不应把已被新连接接管的玩家标记为掉线`（`{ todo: true }`）

## 7. 修复建议
- 在 `handleDisconnect(socket)` 顶部加归属校验：`if (player.socketId !== socket.id) return;`（旧连接的迟到事件直接忽略）。
- `disconnect` 事件里的 `clearPlayerTimers(socket.playerId)` 同样应加同样的归属判断，避免旧连接清掉新连接的定时器。
- 若希望更强：`rejoin` 时对旧 socket 主动 `socket.disconnect(true)`（或记录 `retiredSocketIds`），让旧连接不再产生副作用。

## 8. 备注
Wave 0 之前的 `rejoin` 没有令牌校验，任何知道旧 id 的人都能顶号（BUG-004）；本缺陷是同一段逻辑在**令牌校验补齐之后**遗留的另一半问题，不降低 BUG-004 的修复价值。
