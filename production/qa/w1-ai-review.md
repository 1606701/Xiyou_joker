### A1 · AI 会不会把牌桌卡死 —— 最关键的一条

核心不变量：**任何时刻都不允许出现「`phase === 'playing'` 且 net 定时器 0 个」**。探针在整局推进过程中每 1~3ms 采样一次账本，一旦命中立即记录现场（`currentPlayerId` / `tablePile` / 时间点）。

| 子场景 | 构造 | 结果 |
|---|---|---|
| A1-a 张数不匹配 | 门槛 3 张、AI 手里只有 2 张同点 + 1 张异点 | 无死桌；**21 步打到 settling**，真人 0 error |
| A1-b 手牌为空（摸牌堆 0） | AI 手牌 `[]`，摸牌堆清空 | 无死桌；**45ms 内结算**（`pickUp` 见摸牌堆空即 `settleGame`） |
| A1-b 手牌为空（摸牌堆 20） | AI 手牌 `[]`，摸牌堆留 20 | 无死桌；**653ms / 8 步打到 settling**（补牌后继续） |
| A1-c 幽灵门槛牌 | `topCard` 指向一张不在任何手牌/牌堆/桌面来源的虚构牌 | 无死桌；**19 步打到 settling**（引擎只用 `kind/rank/count`，不反查牌源） |
| A1-d 策略必然抛错 | monkey-patch `ai.chooseMove` 直接 throw | 无死桌；**降级 `autoPlay` 被走过 37 次**（单次运行的计数，随牌局随机性浮动，断言只要求 ≥1）；**20 步到 settling**；真人 **0 error**（降级不惊动玩家） |
| A1-e 三级降级全崩 | `chooseMove` 与 `engine.autoPlay` 同时 throw | **本局被强制结算**（`phase=settling`）；真人收到 **1 次 `INTERNAL`** + **1 次 `gameEnd`**；**残留托管定时器 0 个** |

> A1-e 是这套设计里最值得肯定的一处：宁可异常结束并告诉玩家，也不留「0 定时器 + 一直等 AI」的死桌。实测确实做到了。

### A7 · 跨局生命周期（额外做的，工程侧未覆盖「AI 定时器跨局」这一点）

1 真人 + 2 AI，**连打 5 局**，每局走完 `playing → settling → nextRound → waiting → start`：

- **55 条断言全绿，各连跑 3 次一致**；
- 每局 **13~21 步**人类驱动即可到结算；**最大同时在线 net 定时器恒为 2**（不随局数增长）；
- 每局结算 `results` 覆盖全部 3 人、**通杀者 = 败牌最少者**、真人恰好收到 1 次 `gameEnd`、**全程 0 error**；
- `nextRound` 后 **AI 保持 `ready: true`**（`engine.nextRound` 里 `p.ready = !!p.isAI`），否则房主会永远等不到「全员准备」——这是 AI 补位最容易漏的一处，实测没漏；
- 下一局先手 = 上局通杀者，**先手是 AI 时也正确**（R4 实测 `currentPlayerId` = 通杀的那个 AI）。

## 4. 观察项（不阻断，登记备查）

### P3-1 · `addAI` 的昵称兜底 `AI-${seat + 1}` 是**不可达死代码**

`net/net.js:626`：`const name = ai.AI_NAMES.find((n) => !used.has(n)) || \`AI-${seat + 1}\`;`

**论证**：`addAI` 成功的必要条件是 `room.players.length < 6`（否则先返回 `ROOM_FULL`），即房内已有 **≤ 5 名**其他玩家；真人昵称有唯一性校验（`joinRoom` 里 `players.some(p => p.name === name)` → `NAME_TAKEN`），AI 名字也互不相同，所以 ≤5 名玩家最多占用 **5 个不同昵称**，而 `AI_NAMES` 有 **6 个** → `find` **必然命中**，`||` 右侧永远不执行。

**影响**：无功能影响（兜底不会算错），但它带来一个**误导**——读者会以为存在「6 个 AI 名都被占」的分支，从而误判边界。建议删掉，或改成注释说明「理论不可达，仅防 `AI_NAMES` 被改成小于 6 项」。
**证据**：探针 A4-a/b/c（含「5 个真人占掉 5 个 AI 名」的构造）实测全部走到 `find` 分支。

### P3-2 · `pickUp` 在「空手 + 摸牌堆空」时直接结算（不可达状态下的优雅降级）

我构造的 A1-b 状态（AI 手牌 `[]` 且摸牌堆 0）在正常对局中**不可达**：`resolveNext` 会跳过手牌为空的玩家，`startGame` 也给每人发 5 张。但一旦通过构造/未来改动出现，行为是「立即 `settleGame`」而不是卡死或抛错 —— **这个降级方向是对的**，记录备查，不建议改。

### P3-3 · 平衡数据不足以支撑任何结论（提醒别被数字带偏）

A7 里我顺带记了胜负：15 局中「真人」赢 4、AI 赢 11。**这不能作为「AI 太强」的证据** —— 探针里的「真人」驱动用的是 `beats[0]` 的极简策略，而 `ai.js` 开轮会挑**张数最多**的同点组，两者策略强度不对等。要判断平衡必须让同一策略对打或换成真人 playtest。此数据仅作为「对局能正常分出胜负」的旁证。

## 5. 我没能验证的部分（不写「基本可用」）

1. **真实浏览器里的视觉/交互效果**：AI 徽标和 `·AI` 的实际排版、6 人局座位是否重叠、窄屏（≤390px）下按钮是否挤压 —— 假 DOM 不提供布局能力，**完全未验证**。
2. **多人真实并发时序**：所有验证都在单进程 + 假 socket 上完成。真实 Socket.IO 多客户端、AI 与真人操作真并发交错（同一 tick 内两个客户端同时 emit）**未验证**。
3. **弱网 / 断流 / 长延迟**：AI 思考 800ms（默认）与真实网络 RTT 叠加后的体感，以及「AI 回合中真人网络抖动」的表现，**未验证**。
4. **AI 策略质量本身**：`lib/ai.js` 的决策是否「打得像人」「难度是否合适」，属设计/体验范畴（`design-strategist` 的活），我只验证了「不非法、不卡死」。
5. **长时间稳定性**：最长只跑了 5 局连打（约 90 步）。1 小时以上、几十局的定时器/内存表现**未验证**。
6. **`aiThinkMs = 800` 默认值下的真实节奏**：探针为提速把 `aiThinkMs` 压到 2~40ms，默认值下的「看得清谁出了什么」这一体验目标**未验证**。
