## 0. 判定

# ❌ FAIL

**一句话理由**：Wave 0 声明的 BUG-001~006 六项修复质量高、防假绿能力也强（4 个变异点全部被测试抓住），但独立对抗性测试挖出一个**既有 P0（`BUG-007`）**：按 GDD §6.3 明确允许的合法操作「新一轮开轮打出 A 或 2」会让房间**永久卡死且无任何托管兜底**，并且同样弹出「操作失败」——正好命中 GATE-0 标准 2（挂机不卡局）与标准 5（不再出现「操作失败」）的验收承诺。5 条标准中有 2 条无法签字，因此 GATE-0 不放行。

**重要区分（对 engineering-lead 公平的评价）**：

| 维度 | 结论 |
|---|---|
| Wave 0 声明的范围（BUG-001 修复 + BUG-002~006 收敛 + CI/engines） | **质量合格**，未发现回归或假绿；6 项均有针对性用例，4 个变异点均被抓住 |
| GATE-0 五条验收标准（面向用户承诺） | **不成立**，被一个 Wave 0 未引入、但恰好落在验收口径内的既有 P0 击穿 |

> P0 是既有缺陷（`git diff lib/` 为空，`lib/engine.js` 与 HEAD 完全一致，v1.0/v1.1 阶段即存在），**不是本次改动引入的**。但「止血」这一波的验收口径是用户可感知的可用性，所以它必须计入判定。

### 1.1 逐条说明

**标准 1 — 用例数已达标，但「全绿」要多说一句**

- 用例数：**83**（`cards 17 + engine 25 + net 25`=67 原有，`net.adversarial 16`=本次新增），远超 57。
- 执行结果：`# tests 83 / # pass 78 / # fail 0 / # todo 5`，`npm test` 退出码 **0**（CI 不会因此变红，已实测）。
- ⚠️ 但**这 5 条 `todo` 不是通过，而是「按应然行为书写的已知缺陷用例」**：它们此刻内部是红的（真实失败），只是以 TODO 形式报告，避免「已知缺陷把 CI 弄红导致没人再看 CI」。它们分别是：
  1. `缺陷 P0-01` —— 开轮打功能牌 → 下家收不到 `yourTurn`（BUG-007）
  2. `缺陷 P0-01b` —— 开轮打 A 后收牌也抛错（BUG-007）
  3. `缺陷 P1-02` —— 旧 socket `disconnect` 误标掉线（BUG-008）
  4. `缺陷 P2-02` —— 陈旧定时器改写幽灵房间（BUG-009 P2-02）
  5. `缺陷 P2-01` —— `dispose` 不清宽限定时器（BUG-009 P2-01）
- 因此严格表述是：**「83 条用例、0 条回归失败、5 条已固化的已知缺陷」**。修完 BUG-007 / BUG-008 后去掉对应 `todo` 即为红线。

**标准 2 — 超时托管机制真的生效，但「不卡局」不成立**

真实计时探针（生产默认参数，3 人房，全员挂机，观察 190s，详见附录 B）：

```
[0.0s]  开局 current=p0 tablePile=0
[30.2s] p0 被超时托管 → 出牌，回合交给 p1          ← 30s 回合托管
[60.1s] p1 被超时托管 → 出牌，回合交给 p2
[61.7s] p2 无可压牌 → 1.6s 内自动收牌（败牌 +2）    ← 1.5s 自动收牌
[91.7s][121.7s][151.8s][183.1s] 继续每 ~30s 推进
结果：8 次回合推进、yourTurn 下发 8 次、客户端 error = 0、无卡死
```

→ 托管链路在**生产默认参数**下确实工作（这正是 BUG-001 修复的核心价值）。
→ 但同一套机制在 BUG-007 面前**完全失效**：因为崩溃发生在 `sendTurn()` 调度定时器之前，**一个兜底定时器都不会被创建**。实测挂机 35s（>30s 回合托管 + >1.5s 自动收牌）后房间零推进、零定时器。

**标准 3 — 1.5s 自动收牌，PASS**

- 真实计时：`60.1s → 61.7s`（= 1.6s，含 250ms 采样粒度；`pickupDelayMs = 1500`）。
- 另有注入计时用例（他的 `回归 BUG-001：无合法牌 → 定时器自动收牌` 与我的 `对抗 1/10`）做交叉校验。

**标准 4 — 掉线 60s 后回收，PASS（含一条 P2 细节）**

- 真实计时：p0 掉线于 0ms → 房间于 **60063ms** 从 `rooms` 移除（误差 63ms）；掉线 8s 快速托管实测 **8085ms**（`disconnectedTurnMs = 8000`）。
- P2 细节（`BUG-009 P2-10`）：宽限期是**按玩家**计的，但删房由「最早到期的那次宽限回调 + 全员离线」触发，因此**后掉线者的宽限会被提前截断**（实测 p1/p2 只拿到 51s 而非 60s；极端情况可接近 0s）。

**标准 5 — 「不再出现操作失败」不成立**

- ✅ 原 BUG-001 误报路径已消除：他 的 `回归 BUG-001：出牌后调用 sendTurn 不抛异常` 用例为绿；我的 `对抗 1（6 人整局）` 与 `对抗 10（20 次循环）` 逐帧断言「任一 socket 的 error 事件必须为空」，全程 0 错误。
- ❌ 但合法操作仍会产生**一模一样**的 toast：
  ```
  error { code: 'ERROR', message: "Cannot read properties of null (reading 'kind')" }
  → public/app.js:25 ERROR_TEXT.DEFAULT = '操作失败'
  ```
  触发条件：**桌面为空（新一轮首张）时打出 A 或 2**（GDD §6.3 明确允许）。这是「真错误被当成误报」，比「假误报」更糟：它同时卡死房间。
- ⚠️ **浏览器 toast 本身未验证**：无浏览器/客户端库，只验证到「服务器确实发了 `error` 事件 + 前端映射表里 `ERROR` → `操作失败`」。

## E. P2-01 假红线：他指出的问题**成立**，已修正，现在是真红线

**成因（他判断正确）**：我原来的 `rig.dispose()` 是
```js
dispose() { try { net.dispose(); } finally { ledger.restore(); } }
```
`ledger.restore()` 会 `live.clear()` 把账本清空 → `assert.strictEqual(ledger.timeouts().length, 0)` **恒真**。也就是说这条用例在 v1 里无论产品好坏都是绿的，是典型的**假绿**。这是我自己套件里的缺陷，他 cross-check 出来，我复核后确认。

**修法**：
```js
netDispose() { net.dispose(); },                                  // 只调被测对象，不动账本
dispose() { try { net.dispose(); } finally { ledger.restore(); } }, // 收尾才还原
```
断言改成「`net.dispose()` 之后、`ledger.restore()` 之前」先对账本做快照，再比对残留数量。

**修正后结果：真红线（正确保持 RED）。** `t.diagnostic` 实测残留 **1 个 `600000ms` 定时器**（`reconnectGraceMs = 60s` 的掉线宽限）——`net.dispose()` 只清 `gcTimer` 与 `timers` Map，**不清 `graceTimer`**。这是真实缺陷（热重载 / 测试环境残留 10 分钟定时器，且触发时会去改写已销毁的房间）。该条以 `{ todo: true }` 暂挂，编号 P2-01，已登记进 `BUG-009.md`。

**这条值得记一笔**：我 v1 报告里有 1 条「证据」其实是假的。它没影响 v1 的 FAIL 判定（FAIL 是靠 BUG-007 实锤的），但它是我这次最大的自省点——**变异测试不只该对着产品代码做，也该对着自己的断言做**。
